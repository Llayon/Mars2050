## 1. Задача и заранее объявленный критерий

Проверить, можно ли ускорить детерминированную тригонометрию `packages/combat-core`
на полном бое, не меняя ни одного бита результата. Разрешалось менять только
вычисление, сохраняя формулы, порядок операций, ветвления, RNG, порядок обхода,
события, публичный API, валидацию и форматы replay/save. Запрещались приближённые
формулы, округление, расширение допусков, кэши с состоянием между боями, ECS/фазы/
коллизии/снимки/журналы, а также смена рантайма, сборщика или зависимостей.

Критерий успеха был зафиксирован до реализации:

| Условие | Порог |
| --- | --- |
| Микробенчмарк изменённой функции | `≥ 1.10×` |
| Полный бой `massive_clash`, медиана по-парных | `≥ 1.02×` |
| Полный бой `zerg_rush`, медиана по-парных | `≥ 1.01×` |
| Побед по парам | `≥ 7 / 9` на каждый пресет |
| Null-контроль (тот же код с двух сторон) | `1.000 ± 0.015` |
| Хеши полного результата | совпадают с O2.2 |
| 0-ULP | ни одного расхождения |

Протокол: 9 пар, 5 прогонов на процесс, прогрев 2, чередование порядка
baseline/candidate по парам, cooldown 1500 мс, baseline внутри того же дерева
(общий `zod`), полная сверка хеша результата на каждом прогоне, включая null.

## 4. Кандидат

Переработан только `packages/combat-core/src/math/trig-atan.ts` (diff —
`evidence/candidate-trig-atan.patch`):

1. Коэффициенты полинома `aT[0..10]` вынесены в скалярные константы `aT0..aT10` —
   убирается загрузка из массива, порядок сложения и умножения не менялся.
2. Тело `deterministicAtan` вынесено в `atanCore(x, hx)`: вызывающий уже имеет
   `highWord(x)` и не читает его повторно.
3. В `deterministicAtan2` `lowWord(y)`/`lowWord(x)` читаются только в тех ветках,
   где они действительно нужны; проверки `(iy | ly) === 0` и `(ix | lx) === 0`
   заменены на эквивалентные `iy === 0 && lowWord(y) === 0` и
   `ix === 0 && lowWord(x) === 0`.
4. Внутри `atan2` для `atan(|y/x|)` переиспользуется уже прочитанный `highWord`.

Ни одна формула, константа, ветка, порядок операций и публичная сигнатура не
изменены. Кандидат собирался штатным `npm run combat:core:build`; A/B сравнивал
`packages/combat-core` (кандидат) с `.tmp/base-o22` (принятые байты).

## 7. Почему кандидат отклонён

1. **Потолок участка ниже разрешения.** Вся тригонометрия — 2.9–3.6 % CPU ядра,
   atan-семейство — 2.4–2.8 %. При ускорении функции на 2.3 % максимальный
   эффект на бой — `0.06–0.10 %`. Наблюдённые `4.3 %` / `1.1 %` примерно
   в 11–43 раза больше этого потолка, то есть это не эффект патча, а дрейф станции.
2. **Null-контроль это подтверждает.** Один и тот же код, измеренный дважды,
   расходится на `3.5 %` и `7.4 %` — в десятки раз больше потолка. При таком
   дрейфе 9 пар не могут разрешить эффект `0.1 %`.
3. **Побед 5/9 при пороге 7/9.** Численные `1.043×` / `1.011×` получены при
   разбросе `0.76…1.38`; принимать их как доказательство нельзя — это было бы
   выборочным чтением шума.
4. **Микробенчмарк не дал требуемых 10 %.** Даже изолированная функция ускорилась
   только на 2.3 % (4/7 побед), что согласуется с потолком и не оправдывает
   изменения в горячем математическом модуле.

Точность — не причина отказа: кандидат бит-в-бит равен O2.2 на 2.5 млн проверок.
Причина — измеримость. По условию задачи при неотличимом от шума выигрыше
кандидат не предъявляется.

## 10. NOT_RUN и ограничения

* **Linux CI, Mars-набор, golden V8/V9, browser/package-проверки — NOT_RUN**:
  кандидат отклонён, новых байтов нет; после возврата `dist` побайтово равен
  принятому архиву (912/912), поэтому подтверждения именно `o22mv.1` остаются
  в силе.
* **Fantasy worker/UI** не измерялся; профили сняты на нативном бандле, фикстуры
  только читались. Vendor, зависимости и флаги не менялись.
* **Память** отдельно не сравнивалась: кандидат отклонён по времени.
* **Микробенчмарк** использовал лабораторный ESM-порт `atan-v2.mjs`, а не
  собранный CJS-модуль: к моменту финального прогона репозиторий уже был
  возвращён к baseline. Обе реализации — один и тот же алгоритм, что
  подтверждено 0-ULP-проверкой; для вывода «2 %, а не 10 %» этого достаточно.
  Первый, несохранённый прогон дал ~`1.019×` на том же наборе аргументов.
* **Шум станции**: null-контроль `0.965×` / `0.926×`, дрейф между блоками
  измерений. Все сырые прогоны сохранены, включая шумные.
* **Профиль завышает мелкие неинлайнящиеся кадры** (находка O2.3), поэтому доли
  тригонометрии — верхняя оценка, а не точная стоимость; вывод об отказе от
  этого не зависит.

## 11. Вывод для следующего среза

Тригонометрия как участок закрыта: точных алгебраических сокращений, которые
сохранили бы порядок fdlibm-полинома, здесь нет, а оставшиеся 2–3 % CPU делятся
между `atan`, `atan2`, `sin/cos` и битовыми операциями. Ускорять одну функцию на
2 % при доле 0.7 % бессмысленно — эффект ниже любого честного порога.

Следующий срез должен начинаться не с математики, а с участков, которые профиль
показывает крупнее: `generateVectorField` (2.04 % / 0.18 %) и `getDistance`
(1.33 % / 1.93 %); в O2.3 отдельно измерялись пары коллизий (`visitBucketPair`,
`buildAllPairs`) и защитный снимок `begin`. Каждый из них требует отдельного
решения по владению данными и отдельного 0-ULP/порядкового доказательства; ни
один в O3.0 не трогался. Порог успеха должен проверяться тем же протоколом
с null-контролем: при дрейфе станции 3–7 % микробенчмарк функции обязан
показывать заметно больше 10 %, иначе полный бой эффект не разрешит.
