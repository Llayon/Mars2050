# План оптимизации производительности combat-core (Фаза O)

Дата: 2026-10-14.  
Статус: `approved_for_planning` (задача открыта после завершения и коммита сертификации R7 `177b213`).  
Базовый коммит R7: `177b2132119e202f0770b7bb66068518922aac90`  
Исторический Mars baseline: `0097e7d777582be8ea45319f66edae1cf910e6b0`  

---

## 1. Контекст, статус потребителей и цели оптимизации

В рамках сертификации R7 автономность пакета `@mars2050/combat-core`, изоляция публичного контракта и строгий побитовый детерминизм (100% bit-for-bit между Node.js 22/25/26 и Chromium) подтверждены и зафиксированы. При этом зафиксирована документированная регрессия производительности:

- **`massive_clash`** (100 юнитов, 73 тика, 5 509 действий):  
  Baseline: **202.64 ms** $\rightarrow$ R7: **803.55 ms** (замедление в **×3.965**, дельта **+600.91 ms**).
- **`zerg_rush`** (605 юнитов, 184 тика, 69 653 действия):  
  Baseline: **5 267.79 ms** $\rightarrow$ R7: **9 089.70 ms** (замедление в **×1.726**, дельта **+3 821.91 ms**).

### Статус Fantasy и разделение контуров замера:
Fantasy по-прежнему использует зафиксированный **SDK52** (`52a91f4e...`), что подтверждено зависимостями клиента и бэкенда. Любые оптимизации устаревшего адаптера Mars (`combat.compat-mapper.ts`) автоматически Fantasy не ускорят.  
Поэтому в оптимизационной фазе замеры ведутся по двум независимым контурам:
1. **Прямой контур ядра (Pure Core Path)**: Прямой вызов `simulateBattle` из `@mars2050/combat-core` (актуально для чистых потребителей и будущих версий Fantasy).
2. **Контур совместимости Mars (Mars Compat Path)**: Вызов через адаптер обратной совместимости Mars (`src/domains/combat/combat.compat-mapper.ts` и `combat.service.ts`).

### Доказанные источники затрат (по данным V8 CPU Profiler):

1. **Граница DTO и адаптер Mars**: **2 078.04 ms (54.37% дельты `zerg_rush`)**:
   - `outputSchemaValidation` (611.52 ms медиана, 1 506.48 ms / 15.20% CPU времени в профиле): полный обход и валидация 69 653 элементов массива `CombatAction` через Zod `safeParse`.
   - `mapBackToMarsBattleResult` (1 105.30 ms медиана, 484.94 ms / 4.89% CPU времени): распаковка и трансляция типизированных действий обратно в legacy-формат событий Mars.
   - `validateInputSchema` + `mapReplayAndRuleset` (358.06 ms медиана): валидация входных данных и метаданных.
2. **Цикл ECS симуляции (`rawEcsTickLoop`)**: **1 591.95 ms (41.65% дельты `zerg_rush`)**:
   - Численная детерминированная тригонометрия (`trig-atan.ts`, `deterministic-trig.ts`, `trig-bits.ts`): **221.56 ms (2.23% CPU self-time)** из-за отсутствия нативного inlining MSVCRT в V8.
   - Многостадийный планировщик стадий симуляции и диспетчеризация действий.
   - Нагрузка на сборщик мусора (GC CPU self-time вырос с **60.53 ms** до **196.70 ms**) из-за per-tick аллокаций векторов, действий и временных структур.

## 2. Незыблемые архитектурные правила и ограничения

1. **Не отключать валидацию результата и не удалять «неудобные» поля**:  
   Публичный API обязан гарантировать полноту и корректность возвращаемых данных. Никаких флагов вроде `validateOutput: false`, отказа от проверок в пользу «типов TypeScript» **или удаления/усечения полей схемы (`CombatAction`, `details`, `targetMark`, `statusEffects` и т.д.) ради облегчения валидации**. Контракты данных остаются на 100% полными, неизменными и строго валидируемыми; оптимизация должна устранять исключительно дублирующуюся работу, избыточные проходы и лишние трансформации.
2. **Изоляция переиспользуемой памяти от истории боёв**:  
   Любые пулы объектов и буферы памяти допустимы **исключительно для эфемерных промежуточных вычислений внутри отдельного тика или отдельного боя**.  
   Уже сформированные события, действия, снимки состояния (`CombatAction`, `CombatReplay`, `BattleResult`) **ни в коем случае не должны удерживать ссылки на переиспользуемые мутабельные буферы**, чтобы исключить повреждение результатов завершённых боёв при запуске следующих.
3. **Эмпирический подход (замеры после каждого шага, а не обещания заранее)**:  
   Любые оценки ускорения являются гипотезами, а не гарантированными цифрами. Каждый срез внедряется изолированно, после чего проводятся строгие прогретые замеры прямого и Mars-контуров и проверка идентичности реплеев.
4. **Математика симуляции пока неизменна**:  
   Математические функции (`deterministicAtan2`, тригонометрические ядра) и порядок симуляции на начальном этапе не модифицируются, чтобы гарантировать 100% стабильность золотых реплеев и межплатформенного детерминизма.
5. **Неприкосновенность SDK52**:  
   Пакет Fantasy SDK52 (`52a91f4e...`) и прототипы `apps/fantasy` остаются нетронутыми.
6. **Архитектурные лимиты**:  
   Соблюдение `scripts/check-limits.ts`: Routes $\le 80$, Configs/Contracts $\le 100$, Services/Modules $\le 250$, Hooks $\le 150$. Запрет `: any` / `as any`.

## 3. Рабочие срезы оптимизации

Реализация начинается **строго со среза O1** (устранение лишних преобразований и аллокаций памяти в граничном слое и адаптере).

### Срез O1: Устранение лишних трансформаций и аллокаций в граничном слое (Текущий фокус)

- **O1.1: Оптимизация валидации без отключения гарантий контракта**:
  - Исследовать структуру валидации `CombatRunResult`: устранить дублирующие проходы и каскадные проверки одних и тех же полей.
  - Оптимизировать парсинг повторяющихся структур действий (`CombatAction`), избегая создания промежуточных объектов валидатора там, где Zod выполняет избыточное глубокое клонирование.
  - Сохранить 100% гарантию валидности контракта для всех вызывающих сторон (без удаления, усечения или игнорирования полей схемы).
- **O1.2: Прямая трансляция действий в адаптере Mars (`combat.compat-mapper.ts`)**:
  - Устранить создание промежуточных временных массивов при маппинге действий ядра в legacy `BattleResult`.
  - Предвыделять результирующий массив фиксированной длины `new Array(actions.length)` вместо динамических `push`.
  - Оптимизировать сборку строк и ключей в `serializeCombatEvent`.
- **O1.3: Измерение эффекта O1**:
  - Замерить прямой контур ядра (`simulateBattle` в pure runner).
  - Замерить контур совместимости Mars (`simulateBattle` через `combat.service.ts`).
  - Проверить 100% побитовое совпадение реплеев Mars V8 (7/7) и V9 (7/7).

### Срез O2: Эфемерные пулы промежуточных вычислений внутри ECS-цикла (После завершения O1)

- **O2.1: Изолированные эфемерные буферы для per-tick расчётов**:
  - Использовать переиспользуемые плоские массивы/буферы для spatial hash query candidates и расчёта дистанций/векторов `(dx, dy)`.
  - Строго гарантировать, что ни один объект из пула не утекает в результирующие массивы действий или реплея.
- **O2.2: Сокращение аллокаций в диспетчере тиков**:
  - Устранить создание одноразовых объектов параметров при передаче контекста между системами внутри кадра.

### Срез O3: Детерминированная тригонометрия (Только при подтверждённой необходимости)

- Оптимизация алгоритмов тригонометрии отложена до завершения O1 и O2. Любые изменения в этом срезе потребуют отдельного доказательства 0-ULP эквивалентности и проверки на матрице сред.

## 4. Протокол проверки каждого шага

Для каждого изменения:
1. Запуск unit-тестов ядра (`npm run test:combat:core`, 279 тестов).
2. Запуск тестов Mars (`npm test`, 864 теста).
3. Проверка золотых реплеев V8 и V9 (`npm run combat:ecs:golden`, `npm run combat:ecs:v9:golden`).
4. Замер производительности (прогретые прогоны `massive_clash` и `zerg_rush` для прямого контура ядра и контура Mars).
5. Проверка архитектурных ограничений (`npm run lint:limits`).
