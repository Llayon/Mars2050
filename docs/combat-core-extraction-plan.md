# План выделения общего combat-core

Дата: 2026-09-09. Статус: план; этапы E0–E7 и ранний рубеж B1 ещё не выполнены.

Цель: Mars2050 и Fantasy используют одну реализацию боя через независимый TypeScript-пакет. Пакет собирается, тестируется и запускается без приложения Mars2050, его БД, контента и переменных окружения. Результаты существующих боёв Mars сохраняются.

## Исходная точка

- GitHub `master` на момент проверки: `0097e7d777582be8ea45319f66edae1cf910e6b0`; [PR15](https://github.com/Llayon/Mars2050/pull/15) слит 2026-08-19. Повторный merge PR15 не требуется.
- Аудит исходников выполнен на `50fd9b7` в `feat/map-terrain-pipeline`. Дерево `src/domains/combat` совпадает с локальной веткой PR15 на `5bad354`; тестовые деревья веток различаются.
- При подготовке передачи выполнен `git fetch origin master`: `origin/master` обновлён до `0097e7d`, merge-объект доступен локально. Это синхронизация Git, а не выполнение E0; новый запуск обязан снова подтвердить фактическую базу и тесты.
- Документы передачи подготовлены в отдельной ветке `docs/combat-core-agent-handoff` от этого `master`. Незапушенный terrain-коммит исходной `feat/map-terrain-pipeline` и локальные отчёты не входят в эту ветку или перенос движка.
- При первоначальном аудите прошли 28 тестов из пяти файлов: V8/V9 goldens, engine, ability compiler, unit compiler. Это не заменяет полную проверку baseline в E0.
- PR10–PR15 — диагностические и регрессионные опоры. Они не доказывают независимость результата от произвольного переименования ID или перестановки участников.

## Принятые границы

```text
Mars2050 UI/API -> Mars adapter -> combat-core <- Fantasy adapter <- Fantasy

packages/combat-core/
  src/index.ts             публичный фасад
  src/contracts/           независимые типы и Zod-схемы
  src/compiler/            определения боя -> внутренние программы
  src/runtime/             цикл боя и контекст запуска
  src/ecs/                 закрытые stores, scheduler и systems
  src/replay/              явный кодек публичных событий и снимков
  tests/                   самостоятельные тесты ядра
src/domains/combat/        адаптер Mars, контент, найм и игровые сервисы
examples/fantasy-combat/   отдельный небольшой потребитель пакета
```

Это целевые пути, а не уже созданные модули. Достаточно одного общего пакета и адаптеров в доменах игр. Перенос приложения Mars в `apps/`, создание полноценного Fantasy UI и публикация в registry не входят в этот план.

| Ответственность | Владелец после выделения |
| --- | --- |
| ECS, scheduler, PRNG, движение, коллизии, атаки, статусы, жизнь сущностей | Ядро |
| Язык поддерживаемых способностей и их компиляция | Ядро |
| Каталоги существ, предметов, улучшений, стоимости и прогрессия | Игра |
| Преобразование DB/ростера в боевые данные и обратно | Адаптер игры |
| Выбор арены, профилей поведения, правил и глобальных воздействий | Игра передаёт данные; ядро исполняет поддерживаемые политики |
| Сериализуемые события и снимки боя | Публичный контракт ядра |
| Хранение replay, совместимость старого DB-конверта, UI и графические ассеты | Игра |

Основные решения:

1. Первая версия поддерживает две стороны и фиксированный шаг `0.1 s`. Это контракт движка; произвольный timestep и несколько команд не добавляются при extraction.
2. Seed обязателен для ядра. Старый fallback `Date.now()` остаётся только в адаптере Mars. Идентичный вход включает порядок, instance ID, определения, правила и версию движка.
3. Функции, ECS-объекты и ссылки на игровые сервисы не входят в `BattleInput`. Правила и способности — проверенные данные; их исполнение происходит в штатных фазах.
4. Каталоги и изменяемое состояние принадлежат одному бою. Допустим только неизменяемый общий набор алгоритмов; глобальная подмена `UNIT_TYPES` и кэш только по `definitionId` запрещены.
5. Входные объекты не мутируются. Каждый юнит получает собственное изменяемое состояние, включая runtime-таймеры, заряды и триггеры.
6. Сохраняются порядок фаз, расход PRNG, порядок spatial queries, инициативы, округления, defense snapshots, commit и replay emission. Канонизация и баланс идут отдельными изменениями.
7. Идентификатор определения существа отделён от instance ID участника боя. Mars сохраняет существующие instance/squad ID: от них зависят инициативы, связи и persistence.
8. Новый API различает ошибки входа и нарушение внутреннего инварианта. Вход проверяется через Zod `safeParse`; неизвестные ссылки и неподдерживаемые комбинации не превращаются в незаметные no-op.
9. Старый replay-формат сначала сохраняется по содержимому и порядку полей. Отделение DTO от ECS не требует немедленного сокращения снимков или переименования событий.
10. Собственная сборка: ESM JavaScript и `.d.ts`; Node.js 22 и Chromium — первоначальная проверяемая матрица. Версии Next/React/Supabase и менеджер пакетов не меняются.
11. Разрешённая runtime-зависимость пакета — Zod для границы входа; остальные текущие алгоритмы остаются на TypeScript/JavaScript. Dev-инструменты сборки и тестов не становятся runtime-зависимостями потребителя.
12. Совместимость старого Mars replay фиксируется в E1. Новый входной API остаётся экспериментальным до проверки обоими потребителями: расширения `BattleRules`, `ArenaSpec` и definitions сопровождаются версией контракта, описанием изменений и тестами. Версия API не подменяет engine/ruleset/replay identity и не разрешает менять Mars baseline.

## Автономное выполнение: Gauntlet-протокол

Протокол не привязан к модели или команде конкретного продукта. [Стартовый промпт](combat-core-agent-prompt.md) предназначен для агента с доступом к репозиторию и терминалу; [шаблон журнала](combat-core-progress-template.md) используется для нового запуска. Модель, клиент и доступные инструменты фиксируются по факту, а не по предполагаемым возможностям Muse Spark или Gemini.

### Подготовка запуска и полномочия

- Прочитать `AGENTS.md`, вложенные инструкции, этот план и существующий журнал. Зафиксировать SHA плана, baseline, ветку, рабочую директорию, чужие изменения, доступные команды, reviewer-сессии и лимиты среды. Публикация документации не означает, что этапы реализации уже выполнены.
- Работать в отдельной implementation-ветке от проверенного `master`, сохранив в ней документы передачи. Если базовый `master` не изменился, можно ответвиться от документационной ветки; иначе перенести только документационные изменения на новую базу и повторить аудит E0. Не брать terrain-ветку за baseline.
- В согласованном scope допустимы локальные изменения, тесты и локальные коммиты принятых срезов. Push реализации, создание PR, merge, deploy, публикация пакета, миграция БД и новые платные сервисы требуют отдельного разрешения. Разрешение опубликовать этот план не даёт таких прав исполнителю автоматически.
- Для unattended-запуска заранее записать заданный пользователем или средой наблюдаемый лимит времени/расхода. Если лимита нет, запросить его до длительной работы; безопасный аудит E0 можно начать. Не увеличивать лимиты, параллелизм или стоимость самостоятельно. Лимит 24 часа, если выбран, является бюджетом, а не обещанием завершить E0–E7.
- У одной рабочей копии один координатор записи. Два агента разных моделей не должны одновременно менять её или переключать в ней ветки; предпочтительный совместный режим — один исполнитель, второй read-only reviewer. Отдельные писатели требуют изолированных рабочих копий и согласованного владения файлами, а не только разных названий веток.

### Цикл одного среза

1. Координатор выбирает ближайший срез с принятыми зависимостями. Записывает цель, разрешённые файлы, запрещённые изменения, критерии приёмки и команды проверки; критерии выводятся из плана, а не придумываются после реализации.
2. Исполнитель вносит минимальные изменения. Аудит и чтение можно распараллеливать; связанные compiler/runtime/ECS/scheduler/spawn/replay-файлы имеют одного владельца записи. Не разворачивать веер исполнителей на пересекающиеся границы.
3. До запуска проверок приостановить запись в исходники проверяемой копии. Зафиксировать snapshot: HEAD, хеш staged/unstaged diff в формате `git diff --binary` и manifest с хешами относящихся к работе untracked-файлов; либо чистый commit. Снимок включает тесты, fixtures, конфиги и lockfile. После любого изменения проверяемых файлов результаты и ревью требуют обновления.
4. Запустить обязательные команды и специализированные проверки среза на этом snapshot; сверить исходники после запуска. Сохранить команду, окружение, exit code, результат и ссылку на лог; для package-check также хеш проверенного архива. `NOT_RUN` или заблокированная проверка не равны `PASS`; прежние результаты другого snapshot не подтверждают новый код.
5. Отдельный read-only reviewer в свежем контексте получает требования, зафиксированный код/diff, baseline и сырые результаты проверок, но не самооценку исполнителя. Проверяет совместимость Mars, границы пакета, полноту тестов и фактическое выполнение приёмки. Для повторного итогового ревью после исправлений использовать новый контекст; это не гарантия безошибочности модели.
6. Замечания reviewer содержат критерий, файл/место, доказательство или воспроизводимый сценарий и способ проверки исправления. Координатор сверяет их с кодом и планом: необоснованное предпочтение не повод менять семантику, а положительный отзыв не отменяет красный тест. Обоснованные нарушения возвращаются исполнителю до повторной проверки.
7. Срез становится `accepted`, только когда все обязательные проверки прошли на том же snapshot, независимое ревью завершено и открытых блокирующих замечаний нет. Отсутствующие субагенты не имитируются сменой роли в одном ответе: подготовить пакет для отдельной сессии/человека, отметить `needs_external_review` и не принимать зависимый этап.
8. Обновить журнал, сохранить локальный checkpoint и самостоятельно перейти к следующему доступному срезу без запроса продолжения. При коммите сравнить итоговое дерево с проверенным snapshot: изменения от hooks требуют повторной проверки затронутого кода. На интеграционных рубежах B1/E5/E6/E7 проверяется также результат сборки срезов вместе.

### Журнал, восстановление и остановки

- Создать `docs/combat-core-progress.md` из шаблона. Фиксировать принятые срезы, текущую попытку, границы файлов, нерешённые замечания, evidence и следующий шаг после каждого цикла, перед compaction и остановкой. Логи и временные архивы не включать в коммиты автоматически; секреты и значения env не сохранять в журнале.
- При возобновлении сверить журнал с реальными Git/files/process state, дождаться или проверить уже запущенные команды, затем продолжить незавершённый срез. Не перезаписывать чужую работу и не повторять принятые этапы без причины; устаревшие доказательства помечать явно.
- Ошибка теста запускает диагностику и исправление, но запрещает переход к зависимому срезу. Три последовательные попытки одного среза без новых подтверждённых данных или устранённого замечания — порог эскалации: сохранить blocker, проверенные гипотезы и требуемое решение, а не бесконечно повторять команды.
- При нехватке полномочий, недоступном независимом ревью, необходимом изменении контракта совместимости или исчерпанном бюджете сохранить частичный результат и остановить зависимую работу. Не ослаблять goldens, assertions, import guards, CI или лимиты ради прохождения цикла; новые регрессионные тесты допустимы.
- Итог запуска различает `completed`, `blocked`, `needs_external_review` и `stopped_budget`. `completed` требует всей Definition of Done и повторной интеграционной проверки последнего состояния. В остальных случаях перечислить реально принятое, незавершённое, выполненные/невыполненные команды, остаточные риски и точный следующий шаг; 24 часа работы сами по себе не являются приёмкой.

## Последовательность поставки

Обозначения E0–E7 — области работ и рубежи приёмки, не номера GitHub и не обязательные монолитные PR. E0 и E1 предшествуют изменению runtime-модели. E2–E4 выполняются малыми вертикальными срезами по графу зависимостей E0; следующий зависимый срез начинается после приёмки предыдущего. Порядок и размер PR уточняются по аудиту, но конечные требования изоляции обязательны.

Рубеж B1 — настоящий автономный бой — выполняется после минимально необходимых срезов E2–E4, до полной сертификации и без ожидания всех вариантов арен. Нужные части фасада E5 и переноса E6 выполняются раньше для B1; E5/E6 затем завершают интеграцию и перенос, а не создают вторую реализацию.

| Этап | Результат | Главный критерий | Риск |
| --- | --- | --- | --- |
| E0 | Baseline, ADR, карта зависимостей | Воспроизводимые эталоны и исходные метрики | Низкий |
| E1 | Минимальный контракт, сериализация и package smoke | Архив устанавливается вне workspace; старый wire-формат совпадает | Средний |
| E2 | Контент и компиляция отделены | Все пути создания используют контекст боя | Высокий |
| E3 | Поведение и правила задаются данными | Нет логики по имени юнита или каталогу игры | Высокий |
| E4 | Арена и физические профили отделены | Нет общих изменяемых размеров/индексов | Высокий |
| B1, внутри E2–E4 | Первый автономный бой через общий фасад | Собственный контент, реальный runtime и архив вне репозитория | Высокий |
| E5 | Завершена интеграция Mars с новым фасадом | PvP/PvE, persistence и replay совместимы | Высокий |
| E6 | Завершены перенос и самостоятельная сборка | Один runtime; пакет не импортирует приложение | Средний |
| E7 | Полная Fantasy/Node/Chromium сертификация | Архивный потребитель проходит всю матрицу сценариев | Средний |

### E0 — зафиксировать исходное поведение

Работы:

- Обновить remote refs, выбрать baseline от актуального `master` после PR15; если он продвинулся, повторить аудит combat-изменений и записать новый SHA. Реализацию вести на отдельной ветке, сохранив terrain-ветку.
- Зафиксировать ADR границы пакета и карту runtime/type/public-import зависимостей. Учесть [детерминизм](../.project/adrs/013-combat-simulation-determinism.md) и [V9 defense snapshots](../.project/adrs/014-combat-ecs-v9-defense-snapshot.md).
- По транзитивному графу выбрать минимальный набор срезов для B1 и записать его блокеры. Проверить не только стартовое создание, но и зависимости scheduler, targeting, traits, spawn и global effects; неиспользуемый в fixture импорт каталога всё равно нарушает границу пакета.
- Снять неизменяемые результаты и fingerprint для V8/V9 goldens, Tier1, PR10–PR15 и дополнительных сценариев границы; записать seed, вход, правила, SHA, Node/OS и команды.
- Добавить baseline-кейсы: отсутствует только X/только Y/обе координаты; препятствия переданы/генерируются; глобальные эффекты; обычный/периодический/on-death призыв; наследование, клонирование и reassembly.
- Подготовить differential harness: текущая реализация против зафиксированных результатов baseline. Не оставлять вторую поддерживаемую копию runtime; для полного A/B использовать исторический commit в изолированном CI checkout.
- Снять пять прогретых запусков `massive_clash` и `zerg_rush` отдельно в production/profile режимах, структурные счётчики и размер клиентского combat bundle.
- Составить inventory тестов и отдельных диагностических CLI PR10–PR15: команды, длительность и уникальные гарантии. Зафиксировать обязательный набор extraction; измерения пока не являются основанием для сокращения проверок.

Приёмка: все относящиеся к combat/replay baseline-проверки проходят. Несвязанные исходные сбои полного набора отдельно воспроизведены и задокументированы; они не разрешают пропускать проверки движка. Baseline-артефакты зафиксированы до первого изменения runtime; неизменность сравниваемых входов проверяется отдельно.

### E1 — минимальный контракт, защита replay и ранний package smoke

Работы:

- Создать каркас `packages/combat-core`, связать его как локальный npm workspace и добавить собственную сборку/проверку контрактов. Контракт доступен через явный package export; root-команды сначала собирают пакет. Адаптеру разрешён импорт контракта; пакету запрещены обратные импорты.
- Согласовать минимальную внешнюю границу: обязательный seed, две стороны, definition/instance ID, сериализуемые вход/выход и identity/version metadata. Подготовить экспериментальные `BattleInput`, `UnitDefinition`, `BattleRules`, `ArenaSpec`, `CombatRunResult`, `CombatReplayUnit`, `CombatEvent`; поля добавлять по проверенным срезам, не проектируя заранее все варианты Fantasy. Названия здесь целевые; опубликованные поля и изменения описываются в PR.
- Предусмотреть явное размещение и нейтральное описание seeded-размещения группы. Расходование PRNG при подготовке остаётся частью запуска ядра, чтобы после подготовки не начинать случайную последовательность заново.
- Описать единицы расстояния/скорости, тики длительности, стороны, команды размещения, определения призываемых существ и поддерживаемые способы завершения. Стоимости, `colony_id`, DB-типы, ECS stores и component bundles исключить из API.
- Валидировать минимальный контракт через Zod `safeParse`; при добавлении возможностей сразу проверять их числа, ID, ссылки spawn/ability/profile, размеры, ограничения боя и совместимость эффектов. Характеризовать поведение старой обёртки на недопустимом входе отдельно от строгого нового API.

### Малые срезы E2–E4 и ранний рубеж B1

Ориентир для разбиения; зависимости E0 могут потребовать выполнить часть следующего среза раньше. Каждый PR включает Mars differential regression, самостоятельный тест изменяемой границы и повторную проверку её транзитивных зависимостей.

| Срез | Что развязываем | Дополнительная проверка |
| --- | --- | --- |
| Стартовые юниты | Подготовленные определения, stats, размещение и ownership | Те же координаты, ID, расход PRNG; frozen-вход |
| Обычные abilities и поведение | Damage/status primitives, traits и targeting profiles | Собственные определения; те же фазы, порядок и Mars baseline |
| Создание во время боя | Все spawn-пути, наследование, клонирование и reassembly | Общий compiler/catalog; настоящий summon без Mars lookup |
| Глобальные воздействия и исход | Scheduled effects и outcome policies | Прежние target/source attribution, terminal timing и replay |
| Арена и физика | Размеры, профили тел, packed cells и spatial context | Стандартная арена совпадает; разные арены не делят состояние |

Не считать срез изолированным только потому, что его fixture не вызывает связанный код. Например, periodic spawn повторно вызывает `compileUnit`: каталог должен приходить из контекста и здесь. Если такой импорт блокирует B1, соответствующую развязку переносим вперёд, а не скрываем импорт сборкой или отключением механики.

Для B1:

- Создать минимального CLI-потребителя в `examples/fantasy-combat` с собственным manifest, двумя определениями существ и боем с существующими damage/status primitives. На первом рубеже допустимы стандартные размеры арены, явное размещение и простое условие завершения; другие размеры и полный набор сценариев остаются в E4/E7.
- Перенести в пакет необходимый замкнутый граф реального runtime и добавить узкий экспериментальный фасад. Mars сразу использует те же перенесённые модули через совместимые обёртки. Обратные импорты в приложение, копия runtime, встроенный Mars-каталог и экспорт `CombatWorld`/stores запрещены.
- При первом переносе сразу обновить сборку, тестовые пути, import guards и охват `COMBAT_DEFENSE_MUTATION` для перемещённых модулей, включая регрессионные тесты этих проверок. Эти обязательные части E6 нельзя откладывать до завершения всего переноса.
- Через архив, установленный вне workspace при недоступном репозитории Mars, выполнить настоящий seeded-бой, повторный запуск и JSON round-trip входа. Сравнить результат и события; параллельно подтвердить Mars baseline на той же реализации.
- Следующим принимаемым срезом после первого боя, если ещё не выполнен, проверить настоящий summon собственного определения через тот же архивный фасад. Не откладывать проверку призыва независимым потребителем до E7; полный набор путей создания сохраняет отдельную приёмку E2.

Приёмка B1: отдельный Node-потребитель выполняет реальную симуляцию со своим контентом, runtime/type-граф поставляемого пакета не содержит зависимостей от Mars. Это раннее доказательство переиспользования, не завершение E2–E4 и не замена полной сертификации E7. При невозможности получить независимый граф сначала устранить выявленные блокеры; не объявлять контрактный smoke автономным боем.

| Пять прогретых production/profile benchmarks | E0, E2–E4, B1, E6–E7 | Нет необъяснённой регрессии времени, счётчиков и размера клиентского кода |
| Полная матрица Node Windows/Linux + Chromium tarball consumer | E7 | Все заявленные сценарии и переносимость проверены вне monorepo |

Планируемые новые scripts: `combat:core:build` — сборка; `combat:core:check` — типы и границы импортов; `test:combat:core` — самостоятельные тесты; `test:combat:compat` — сравнение с baseline; `test:combat:package` — проверка архива с внешним потребителем. Первые три появляются с каркасом E1, compatibility harness — в E0/E1. Package-check вводится в E1 для exports/schema/TypeScript, в B1 дополняется настоящим боем, не позднее следующего spawn-среза — summon, в E7 — полной сценарной и Node/Chromium матрицей. Ранние проверки сохраняются при расширении. Сейчас этих команд ещё нет. Любой существующий test script, импортирующий старые пути, входит в migration inventory.

Сравнение не ограничивается победителем и не сортирует события. Новая версия metadata сравнивается отдельно; исключать можно только заранее перечисленные недетерминированные показатели времени. Старые поля, координаты, optional-значения и порядок массива не маскируются projection-фильтром.

Performance оценивается A/B на одном окружении. Стабильное ухудшение медианы более чем на 10% относительно E0 требует разбора до приёмки; это планируемый порог, не измеренный факт. CI проверяет воспроизводимые структурные счётчики, а не абсолютные миллисекунды на случайном runner.

## После E7 — отдельная оптимизация тестового набора

Это последующая работа, не условие завершения extraction и не разрешение сокращать проверки E0–E7.

- По inventory E0 повторно измерить длительность, частоту запуска и перекрытие гарантий. Различать Vitest-регрессии, отдельные диагностические CLI и investigation-only probes; не считать все CLI уже включёнными в `npm test`.
- Сохранить быстрый постоянный regression suite с уникальными гарантиями: wire/event ordering, PRNG, ownership, spawn, defense и совместимость обоих адаптеров. Совпадение winner/state не заменяет проверку порядка replay.
- Выделить deep determinism suite и явно определить CI-триггеры: изменения соответствующих частей ядра, ночные проверки и перед выпуском. Политику CI и AGENTS менять отдельным согласованным PR; до этого полный обязательный набор остаётся прежним.
- Консолидировать investigation-only probes только при доказанном сохранении уникального покрытия; сохранить исторические артефакты, команды и объяснение выводов. Не обновлять golden-эталоны для устранения расхождений.

## Условия остановки этапа и восстановление

- При расхождении baseline сначала найти первый различающийся input/compiler result/tick/phase. Не менять эталоны, PRNG, ID-order или номер simulationRevision для прохождения extraction.
- При изменении внутренних полей проверить явный wire-кодек E1. Совпадение gameplay-state при изменившемся replay не считается выполненной совместимостью.
- Если Fantasy требует новой механики или изменения scheduler, damage/status semantics либо правил фаз, выделить это в отдельный последующий PR. Критерий ревью extraction: только перенос и параметризация существующего поведения с Mars baseline; новые способности не маскируются под развязку зависимостей.
- При раннем переносе B1 совместимые пути Mars делегируют той же реализации пакета. Возврат к предыдущему принятому срезу выполняется обычным revert конкретного PR вместе с совместимыми импортами и package pin. Не использовать переписывание истории, вторую реализацию или массовую очистку рабочей копии.
- Для эталонного A/B и внешнего потребителя использовать ограниченные временные каталоги/CI checkout. Не создавать постоянные дополнительные worktree и копии приложения только ради плана.

## Технические основания

Локальное связывание пакетов выполняется стандартными [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/). Доступный потребителям API ограничивается [package exports](https://nodejs.org/api/packages.html#package-entry-points); архитектурная проверка дополнительно запрещает обход через исходные пути. Самостоятельность поставки проверяется установкой результата [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/) вне workspace.
